# 版本更新工作流

## 输入

锁定旧版本和新版本的仓库 URL、分支、commit、版本标识及验证环境。任一 commit 未锁定时，不生成确定性的升级结论。

## 步骤

1. 保存旧、新 framework manifest。
2. 获取两个 commit 间的 Git 差异和公开发布说明。
3. 按路径、符号和行为识别受影响模块。
4. 将模块映射到知识卡、上下文包、任务、示例和测试。
5. 将直接或间接受影响知识标为 `needs-review`。
6. 优先运行受影响测试，再运行必要回归集合。
7. 按新证据更新知识、示例和反例，保留历史依据。
8. 生成 knowledge diff，列出新增、修改、废弃、冲突和待复核卡片。
9. 生成 change impact report，说明影响范围、风险和迁移建议。
10. 生成 regression report，记录环境、命令、通过、失败和未运行项。

## 决策规则

源码变化只说明可能受影响，不能独立证明外部行为变化；发布说明也不能替代验证。冲突证据应保留为 `conflicted`。未完成复核的知识不得用于高风险迁移任务。
