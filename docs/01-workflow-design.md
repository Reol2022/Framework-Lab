# 工作流设计

## 目标与原则

工作流把框架版本、证据、知识、任务、验证和反馈连接起来。每个输出都应能回答：针对哪个版本、依据什么、如何验证、何时失效。未执行的步骤不得写成已完成。

## 阶段 0：实验基线

锁定仓库 URL、分支、commit、版本和环境；记录安装、构建、静态检查、示例启动及浏览器验证命令。输出框架清单与基线报告。无法锁定的值标记为 `pending` 或 `null`。

## 阶段 1：学习地图

按学习域列出源码范围、文档范围、官方示例、关键问题、实验和验收任务。学习地图只定义调查路径，不预填未经验证的答案。依赖域优先完成，状态变化需有记录。

## 阶段 2：证据型知识库

将候选结论写成知识卡，绑定框架 commit，附证据、适用条件、反模式、示例和验证记录。只有证据和实验满足规范后才能标记 `verified`；冲突结论保留并标记 `conflicted`。

## 阶段 3：最小上下文包

按任务选择必要知识卡、相关文件和约束，排除无关材料。上下文包记录所引用知识版本、允许读取的路径及额外读取，以衡量上下文规模和知识缺口。

## 阶段 4：分级任务

任务按 L0 至 L5 分级。每项任务明确目标、非目标、前置知识、修改边界、验收标准、命令和预期结果。高等级任务必须建立在低等级任务稳定通过的基础上。

## 阶段 5：统一验证

按任务风险执行环境、静态、构建、运行、行为、边界、兼容、性能和人工体验验证。实际输出写入任务、运行记录或报告；不得用预期结果替代实际结果。

## 阶段 6：问题反馈

每次失败必须保留证据并选择主要类别：

- `framework-bug`
- `documentation-gap`
- `documentation-error`
- `api-design`
- `developer-experience`
- `compatibility`
- `performance`
- `knowledge-error`
- `prompt-error`
- `test-gap`
- `example-error`

完成最小复现后，决定上游反馈、修复实现、修订知识、调整提示或补充测试。一个问题可有关联类别，但必须有一个主要归因。

## 阶段 7：版本增量更新

锁定旧、新 commit，取得差异并映射到知识卡、上下文包和任务。相关知识先标记 `needs-review`，再执行受影响测试。输出 knowledge diff、change impact report 和 regression report。

## 阶段 8：GaitLogic 渐进式迁移

只有迁移门禁全部满足后才进入此阶段。选择可独立回退的低风险模块，先建立旧行为基线，再让新旧页面并存并对照验证。不得以工作流准备完成替代真实迁移授权。

## 失败闭环

失败 → 保存环境与证据 → 分类 → 最小复现 → 定位框架、文档、知识、提示、测试或实现责任 → 修复或确认 → 更新知识与示例 → 新增回归验证 → 重跑相关任务。

分类不是结论：例如运行失败不能自动归为框架缺陷；在证据不足时应记录未知项，并继续缩小复现范围。
