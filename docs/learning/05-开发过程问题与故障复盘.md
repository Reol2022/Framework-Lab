# 开发过程问题与故障复盘

本页只整理已保存的 NCom 验证证据。它不把框架问题归因给 Framework Lab，也不把单次 Windows 结果推广到所有系统。

## 复盘方法

每个问题先固定 commit、环境、命令和原始日志，再区分：命令是否执行、错误是否被完整保存、根因是否被源码或对照实验支持。没有完整 stdout 的历史运行保留为 `evidence-gap`。

## 1. 固定 pnpm 与 frozen lockfile 不匹配

- **发生时间/范围**：Run 001–003；NCom commit `4c1fdf7`。
- **环境**：Node `v21.7.3`；普通 PATH 中 pnpm 一度不可用或为 `11.9.0`，而要求固定 `10.26.1`。
- **现象**：Corepack 下载 pnpm 失败，随后显式固定 pnpm 执行 `install --frozen-lockfile` 返回 `ERR_PNPM_OUTDATED_LOCKFILE`。
- **排查过程**：先确认 PATH pnpm 不是要求版本，再将仓库内 `.framework-tools/.../pnpm.cmd` 放到子进程 PATH 首位；运行才进入 lockfile 校验。
- **根本原因（已确认）**：旧 commit 的 `packages/all/package.json` 与 `pnpm-lock.yaml` importer 不一致。
- **后续结果**：后续 `faf42ba` 在 Node `v24.18.0`、pnpm `10.26.1` 下 frozen install 成功；这只说明后续 commit 不再复现，不能改写旧 commit 的失败事实。
- **修复方式**：Framework Lab 不修改 NCom lockfile；运行器将固定 pnpm 路径配置化，并记录实际版本与 `where.exe pnpm`。
- **验证**：Run 006 记录 user-executed install 成功，但完整 install stdout 缺失，证据等级不是完整日志。
- **防复发**：baseline 配置显式保存 pnpm 可执行路径；所有子进程继承优先 PATH；Run 记录配置版本和实际版本。
- **面试说法**：先解决“工具是否符合要求”，再解释项目依赖失败；不要为了让安装通过换用任意 PATH 版本。
- **追问**：为何 `--frozen-lockfile` 更严格？答：它拒绝隐式更新 lockfile，适合可复现基线。

## 2. Theme build 入口缺失导致 Node MODULE_NOT_FOUND

- **发生时间/范围**：Run 006；commit `faf42ba101975befb79629c63d92e962194e4abe`。
- **现象**：根 `pnpm build` 已进入 `@ncom/all` 再进入 `@ncom/theme`，最终运行 `node scripts/build.mjs` 失败。
- **原始错误要点**：`packages/theme/package.json` 指向 `scripts/build.mjs`，而锁定 Git tree 中没有 `packages/theme/scripts/build.mjs`，Node 以 `MODULE_NOT_FOUND` 退出。
- **最初判断修正**：曾有“`@ncom/all` 缺少 build script”的疑点；实际运行链和 manifest 证明该判断不成立。
- **根本原因（已确认）**：该锁定 tree 缺少 manifest 声明的 theme build 入口文件。
- **处理边界**：未创建空 `build.mjs`，未改 package manifest，也未将猜测的构建产物提交到源码。
- **验证**：Run 006 基线为 `baseline-partial`；构建失败的完整 stdout 当时未保存，因此调用链由 manifest 和 Git tree 交叉确认。
- **是否可能复发**：会；只要该 commit 或具有同一缺失入口的版本被使用。
- **面试说法**：将“脚本不存在”与“构建配置错误”分开，通过 script 链和 Git tree 验证，而不是看到 `ELIFECYCLE` 就停在生命周期包装错误上。

## 3. Vite 开发服务器可监听，但页面入口解析失败

- **发生时间/范围**：Run 007；commit `faf42ba...`。
- **启动命令**：根 script `dev:example` → `pnpm --filter ncom-example dev` → `vite`。
- **环境**：Windows 10、Node `v24.18.0`、固定 pnpm `10.26.1`。
- **现象**：Vite 在约 4.95 秒就绪并监听 `http://localhost:3000/`；`/`、`/@vite/client` 和抽查静态资源返回 200，但 `/index.html?html-proxy&index=0.js` 返回 500。
- **原始错误要点**：`[plugin:vite:import-analysis] Failed to resolve import "@ncom/all/theme/deepblue"`，定位 `example/index.html:15:12`。
- **排查过程**：读取 root/example scripts、workspace 配置和 `example/vite.config.ts`；确认 alias 指向 `packages/theme/dist/ncom-deepblue.css`，测试 worktree 不存在 `packages/theme/dist/`。
- **已确认事实**：example 依赖的 dist theme 文件不存在；这与前述 theme build 入口缺失有关。
- **未知项**：上游预期是提交 dist，还是启动 example 前由某个正式流程生成 dist，尚未验证。
- **验证结论**：`Homepage HTTP: Passed` 不等于应用可用；因为入口模块 500，整体 `HTTP Smoke: Failed`。用户实际看到 Vite overlay，因此 `Browser Behavior: Failed` 是真实人工观察，不是由 HTTP 推断。
- **面试说法**：服务器监听、HTML 返回和页面可交互是不同层级；我分别检查端口、首页、资源、入口模块和人工浏览器状态。

## 4. CJK 绝对路径下 Sass additionalData 构建失败与最小修复对照

- **发生时间/范围**：Run 009/010；base commit `a350b576bbeae6c6254273037a17d2a8730fb80f`。
- **环境**：Windows `10.0.19045` x64、Node `v24.18.0`、npm `11.7.0`、pnpm `10.26.1`。
- **现象**：Run 009 build 失败。结构化错误的首个阻塞事件是 Sass `Can't find stylesheet to import.`，位置为 `packages/components/src/alert/style.scss:1:1`，plugin 为 `vite:css`；lint 的生命周期包装错误没有覆盖该具体错误。
- **排查过程**：确认 `packages/all/build/shared.ts` 的 `createStyleConfig` 会向非 theme SCSS 注入包含 CJK 的绝对路径 `@use ".../packages/theme/index.scss" as *;`；47 个组件 SCSS 已自行显式引用 `@ncom/theme/index`，其余 6 个不使用 theme 变量、mixin 或 function。
- **根本原因（受控对照支持）**：Windows CJK 路径中的 Sass additionalData 绝对 `@use` 使 sass-embedded 无法解析。
- **最小修复**：在独立 detached 候选 worktree 中，只删除 `packages/all/build/shared.ts` 的 `preprocessorOptions.scss.additionalData`。不改组件 SCSS、Vite alias、lockfile、依赖版本或原始 worktree。
- **对照结果**：Run 009：install passed、lint failed（允许失败）、build failed、最终 failed；Run 010：install passed、lint failed（允许失败）、build passed、最终 partial。
- **验证**：候选 worktree 的 tracked 修改只有 `shared.ts`；Run 010 `errors.json` 只含 lint/lifecycle 事件，没有 Sass/Vite build failure，且全局阻塞错误为 `null`。
- **边界**：不证明所有 Windows 版本、所有 CJK 路径都失败；不证明补丁没有功能回归；不宣称上游已接受。
- **面试说法**：我没有直接修原始源码，而是固定 commit、环境和步骤，只改变一个配置点，用 Run 009/010 证明构建状态变化，同时保留 lint 失败。

## 从这些问题得到的通用检查顺序

1. 固定源码 commit 与 dirty 状态。
2. 固定 Node、pnpm、PATH 和实际可执行文件。
3. 区分命令未运行、命令失败和证据缺失。
4. 从具体工具错误回溯到生命周期包装错误之前的首个有效事件。
5. 把端口、HTTP、入口模块和浏览器行为分别验证。
6. 修复实验只改变一个变量，保存 before/after 运行证据。
