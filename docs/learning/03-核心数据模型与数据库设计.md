# 核心数据模型与数据库设计

## 真实情况：没有数据库

Framework Lab 当前没有 MySQL、PostgreSQL、Redis、ORM、HTTP 后端或用户表。它是本地 CLI，使用仓库内 YAML、JSON、JSONL 和 Markdown 作为可审阅产物。面试时不能把本文说成数据库设计经验。

## 可类比的数据模型

| 模型/文件 | 业务作用 | 关键一致性约束 |
| --- | --- | --- |
| `framework.yaml` | 声明 framework、源码、包管理器、baseline step | Schema；相对路径从仓库根解析 |
| `run.json` + environment/source | 一次基线运行事实 | run id 不覆盖；step 独立日志；commit 与 dirty 同时记录 |
| `errors.json` | 日志的结构化事件 | event id/fingerprint、具体错误优先、旧 Run 可兼容 |
| Catalog/Symbol Snapshot | 版本绑定的源码结构 | tracked-only；rootHash 不含时间和绝对路径 |
| KnowledgeCard/KnowledgeUnit | 受证据约束的知识 | Claim 有 Evidence/Scope；旧知识保留历史 |
| Task/Policy/Acceptance/Plan | 受控 Agent 任务状态 | Schema + Git diff + 验证，不信任自报 |
| FrameworkVersion/Impact | 版本差异到知识影响 | Catalog/Symbol Snapshot commit 必须一致 |

## 一致性、幂等与历史

- **幂等/避免覆盖**：run id 创建前存在性检查；Bundle/Task/Snapshot 默认拒绝覆盖；`--force` 仅允许刷新明确的派生产物。
- **原子写入**：Catalog 等输出先写临时目录，经 Schema 校验后移动；Task Manifest 保存文件 SHA256。
- **历史**：Task 和 Learning 使用 JSONL append-only history；旧知识、旧 Run 和旧证据不静默覆盖。
- **版本一致性**：Snapshot 记录 commit/rootHash；Version 创建时校验 Catalog/Symbol 引用；dirty worktree 不表述为纯净 commit。

## 不适用项

没有表关系、数据库索引、事务、用户隔离、数据库迁移或连接池。若未来改成服务化，需要重新设计并验证：身份/权限、项目隔离、并发 run reservation、产物存储、事务边界、审计和数据保留策略。

## 面试回答

“当前没有数据库，因为项目先验证本地可追溯工作流；我把 JSON Schema、hash、原子写和 append-only history 作为文件产物的一致性机制。但我不会将它等同于数据库事务或多租户隔离。”
