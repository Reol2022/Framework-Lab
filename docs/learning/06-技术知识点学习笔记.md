# 技术知识点学习笔记

本页只覆盖当前仓库真实使用或已明确验证的技术。掌握程度是建议自评：`能解释` 表示可以结合本项目讲清用途；`能修改` 表示应能在阅读代码后做受控改动；不等于已在所有场景独立实现。

## Node.js 子进程与 Windows 参数边界

- **它是什么**：Node `child_process.spawn` 以“命令 + 参数数组”启动进程。
- **项目位置**：`cli/lib/process.ts` 的 `buildSpawnSpec`、`runStep`、`startBackgroundProcess`。
- **解决的问题**：执行 NCom 的 pnpm、git、开发服务器，同时保留 stdout/stderr、PID、退出码和超时。
- **核心原理**：`shell:false` 避免把路径和参数交给 shell 再解析。Windows 的 `.cmd/.bat` 不能直接由 CreateProcess 执行，因此仅对这类命令显式适配 `cmd.exe /d /s /c`，并保留参数边界。
- **最小示例**：`spawn(command, args, { cwd, shell: false, stdio: ['ignore', 'pipe', 'pipe'] })`。
- **真实问题**：Windows 中文路径与 pnpm `.cmd`；Run 007 的服务进程也需要 PID、独立日志和可停止会话。
- **常见错误**：把整条命令拼为字符串、设置 `shell:true` 绕过引号问题、混合 stdout/stderr、超时只杀父进程。
- **替代方案**：`exec` 更适合短命令但会引入 shell 与缓冲区边界；本项目选择 spawn。
- **面试问法**：为什么 `spawn` 更安全？如何停止 Windows 进程树？
- **掌握程度**：能解释；应练习改写 isolated test 验证 `.cmd`、空格与 CJK 路径。

## pnpm 固定版本与可复现安装

- **它是什么**：pnpm 是 Node 包管理器；`--frozen-lockfile` 要求 manifest 与 lockfile 一致。
- **项目位置**：`frameworks/ncom/framework.yaml`；`frameworks/ncom/manifest.yaml`；`cli/lib/environment.ts` 与 baseline 运行器。
- **真实用法**：配置固定仓库内 `pnpm@10.26.1` 的 `.cmd`，并把其目录置于子进程 PATH 首位。
- **真实问题**：Run 003 在旧 NCom commit 得到 `ERR_PNPM_OUTDATED_LOCKFILE`；Run 006 的后续 commit 使用同一固定 pnpm 可安装。
- **为什么这样选**：普通 PATH 的 pnpm 可能不存在或版本不同。固定可执行路径比“机器上恰好装了 pnpm”更可审计。
- **常见错误**：把 PATH 版本当成配置版本；为了通过 frozen install 自动更新 lockfile；未记录实际 `pnpm --version`。
- **面试追问**：为何不能通过非 frozen install 掩盖问题？答：那会改变依赖解析结果，不再是原 commit 的可复现基线。
- **掌握程度**：能解释。

## TypeScript、ESM 与 Compiler API

- **它是什么**：TypeScript 提供静态类型与 Compiler API，可分析 TypeScript/TSX 的语法树。
- **项目位置**：`cli/index.ts` 是 ESM 入口；`cli/lib/symbols.ts` 生成 module、symbol、export chain、component 和 relationship 记录。
- **解决的问题**：在不执行 NCom 源码的前提下，定位声明、公共导出、组件候选、Props、事件、样式、文档和 example 关联。
- **真实边界**：仅覆盖 TypeScript/TSX；语义 resolver 不完整时降低 confidence，不把语法分析伪装成完整调用图。
- **最小概念**：AST 把源文件解析为节点；导出链从 package entry 到声明；declaration hash 用于判断结构内容是否变化。
- **常见错误**：把任意 `export` 当成 public API；将 AST 关系推断成运行时行为；忽略 commit/Snapshot scope。
- **替代方案**：正则更容易开始但难处理重导出和类型语法；项目选择 Compiler API。
- **面试问法**：为什么 Catalog 与 Symbol 分层？答：Catalog 只收集 tracked 文件元数据，Symbol 层才消费已登记 TS 文件做语法分析。
- **掌握程度**：能解释；应能阅读 `symbols.test.ts` 中 fixture 后再修改抽取规则。

## CLI 设计与 Codex CLI 边界

- **项目 CLI**：`pnpm framework-lab ...`，入口 `cli/index.ts`，命令覆盖 baseline、errors、catalog、symbols、retrieval、context、task、learn、version。
- **Codex CLI 在本项目中的位置**：Codex 可作为用户侧或外部会话的 Coding Agent；Framework Lab 只生成 Context/Handoff、检查 diff、运行验证，不在核心中自动启动 Codex 或调用 OpenAI API。
- **为什么分离**：避免把 Agent 自报、模型输出和框架事实混为一层；使同一任务可由人工、其他 Agent 或未来工具执行。
- **真实证据**：v0.2.0 任务 Handoff 明确“不启动 Agent”；v0.1.8 的 A/B 是用户交付 Context 给全新外部会话的探索性实验。
- **不应声称**：项目集成了 Codex API、可自动完成代码修改、可自动接受结果。
- **掌握程度**：能解释。

## Git worktree、commit 和 dirty 状态

- **它是什么**：Git worktree 允许同一仓库在不同目录检出不同 commit。
- **项目位置**：`cli/lib/git.ts`、`cli/lib/task.ts`、`cli/lib/catalog.ts`。
- **解决的问题**：让 baseline、修复实验和 Agent 任务不污染原始 NCom worktree。
- **关键实现**：`collectGitSnapshot` 用 `git rev-parse HEAD` 与 porcelain status 采集 commit、dirty 与变更文件；读取失败记录 warning/null，不伪造 clean。
- **真实案例**：Run 010 使用独立候选 worktree，只允许 `packages/all/build/shared.ts` 为 tracked 修改；Run 009 原始 worktree 保持不变。
- **常见错误**：只记录 HEAD 而忽略 dirty；把 `node_modules` 当作补丁；在原 worktree 上验证 Agent 修改。
- **面试问法**：为什么必须记录 dirty？答：同一 commit 加不同未提交改动不是同一输入，不能把它表述为纯净上游行为。
- **掌握程度**：能解释。

## JSON Schema、Ajv 与 Validator

- **它是什么**：JSON Schema 描述数据形状；Ajv 编译 Schema 并验证运行产物。
- **项目位置**：`schemas/*.schema.json`、`cli/lib/schema.ts`。
- **项目做法**：按 schema path 缓存编译后的 validator；失败时返回 instance path 与错误信息。Run、ErrorEvent、Catalog、Symbol、Task、Learning、Version 等产物写入前或校验时使用 Schema。
- **解决的问题**：避免 CLI 输出“看起来像 JSON”却缺字段、类型错或 Scope 不一致。
- **真实边界**：Schema 验证结构，不自动证明语义正确。例如 HTTP 200 仍不能证明浏览器交互正确。
- **常见错误**：把 Schema 校验视为业务验收；为旧数据强制破坏性升级；不保存 manifest/hash。
- **面试问法**：结构校验和业务 Validator 有什么区别？答：前者检查形状，后者检查例如文件是否在允许路径、证据是否属于 Bundle、命令结果是否符合 Acceptance。
- **掌握程度**：能解释。

## 框架源码阅读：Catalog、Symbol 与精确 Diff

- **它是什么**：不直接依赖模型总结，而是从 `git ls-files -z` 开始，扫描 Git tracked 文件、hash、分类、workspace、文档章节、示例与静态配置。
- **项目位置**：`cli/lib/catalog.ts`、`cli/lib/symbols.ts`、`cli/lib/version.ts`。
- **原则**：不执行框架脚本、不动态 import 配置、不复制完整源码；rename 只接受一对一完全相同 hash，不做模糊相似度迁移。
- **真实结果**：NCom Catalog/Symbol Snapshot 绑定 source commit；v0.2.2 将两个 Snapshot 绑定为 FrameworkVersion，再复用已有 Diff 生成 freshness/impact。
- **面试问法**：为什么不用 LLM 阅读整个源码？答：首先需要可重复、可验证的结构证据；模型可以成为外部学习参与者，但不能取代版本和文件事实。
- **掌握程度**：能解释。

## 版本与环境基线、运行记录与失败分类

- **项目位置**：`frameworks/ncom/framework.yaml`、`cli/lib/baseline.ts`、`environment.ts`、`report.ts`、`errors.ts`。
- **运行记录内容**：OS/架构、Node/npm/pnpm、Framework Lab commit、框架 commit/dirty、每步命令、cwd、开始结束时间、退出码、stdout/stderr 路径、最终状态。
- **状态规则**：required step 失败 → `failed`；允许失败 step 失败且 required 全通过 → `partial`；阻塞后未运行 → `skipped`；超时 → `timed_out`。
- **失败分类**：ErrorEvent 先匹配 ESLint、Sass、Vite、TypeScript、Node、pnpm lifecycle，最后才是 generic；具体 Sass 错误优先于生命周期包装错误。
- **真实案例**：Run 009 的 blocking error 是 Sass import failure；Run 010 没有 Sass build failure，lint 失败允许存在，所以最终是 `partial`。
- **掌握程度**：能解释。

## 最小 Context、知识卡与受控学习

- **项目位置**：`cli/lib/knowledge.ts`、`retrieval.ts`、`learn.ts`，以及 `frameworks/ncom/knowledge`、`learning`。
- **知识卡**：Claim 必须有 Evidence、Scope 与限制；不允许将 inferred 结论当作已验证事实。
- **Context**：只取有 commit/hash/行号的受限片段；预算是 `ceil(characterCount / 4)` 的启发式，不是实际 tokenizer。
- **Learning 流程**：Topic → bounded Bundle → 外部 Handoff → Draft → Schema/Evidence validate → 人工 review → publish。系统不自动发布。
- **常见错误**：把全文件塞进 Context；把知识命中说成 RAG；忽略 stale scope；把外部 Agent 输出未经校验地发布。
- **面试问法**：为什么最小 Context 比全文更合适？答：减少无关材料并保留可定位证据，但不宣称已证明 Token 节省。
- **掌握程度**：能解释。

## Coding Agent 工作流、Policy 与 Validator

- **项目位置**：`cli/lib/task.ts`、`schemas/task*.json`、`frameworks/ncom/tasks/`。
- **流程**：TaskProfile → Context/Policy/Acceptance/Verification Plan → detached worktree → Handoff → inspect → verify → compare → close。
- **权限与边界**：Change Policy 约束允许/禁止路径、锁文件、manifest、untracked 文件、二进制和冲突标记；Validator 独立读取 Git diff 和命令结果，不信任 Agent 自报。
- **真实案例**：NCButton 任务 Policy passed，18 项自动 Acceptance passed；浏览器点击不是自动化可观测项，保持 `manual_required`。
- **替代方案**：完全自主循环 Agent；当前不采用，因为本项目优先可审计、可中止、可验证的受控工作流。
- **掌握程度**：能解释。

## 构建、HTTP 与浏览器验证

- **层级**：进程存活/端口监听 → 首页 HTML → 静态资源 → 入口模块 → 页面渲染/交互/控制台。
- **真实案例**：Run 007 证明前几层可部分通过，但入口模块 500、浏览器 Vite overlay，因而 Browser Behavior Failed。
- **项目边界**：不安装 Playwright，不将 HTTP 200 写成浏览器成功；浏览器 checklist 保留给用户人工完成。
- **面试问法**：什么时候 HTTP smoke 足够？答：它只适合确认服务/资源基本可达，不足以证明交互、样式和控制台无阻塞错误。
- **掌握程度**：能解释。

## Agent 配对评测与指标边界

- **真实实验**：v0.1.8 在同一 NCom commit 上对比无 Context 与有 Context 的两个全新 Coding Agent 会话；两组都完成受限 example 修改、构建、开发服务与 HTTP 检查。
- **已支持的结论**：B 组可使用 Context；观察到其减少对核心源码、Props/事件、导出和文档的补充探索；两组均保持修改边界。
- **不支持的结论**：没有保存精确 usage、耗时、读取量或真实 Token；不能证明代码质量提升、固定比例 Token 节省或统计普遍性。
- **如何改进**：未来固定任务、commit、验收、会话启动条件；采集命令数、文件读取、耗时、Token、重试、浏览器人工结果；预先定义成功指标和失败类别。
- **掌握程度**：能解释实验边界；尚不能宣称完成严格 Agent Eval 平台。
