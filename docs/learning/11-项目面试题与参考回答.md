# 项目面试题与参考回答

使用方式：先用自己的话回答，再核对证据和边界。不要逐字背诵，更不要把未实现功能包装成生产能力。

## 第一层：项目介绍

### 1. 请介绍 Framework Lab

**推荐回答**：Framework Lab 是一个本地 Node.js/TypeScript CLI，用于把陌生框架的学习和 Coding Agent 任务变成可追溯流程。我先锁定框架 commit 和环境，再配置化执行 install/lint/build，保存 stdout/stderr 和结构化错误；之后从 Git tracked 源码构建 Catalog 和 TypeScript Symbol 索引，生成带证据的最小 Context。对实际开发任务，我用 detached worktree、Change Policy、Acceptance 和 Verification Plan 约束和独立验证 Agent 修改。当前只在 NCom 上完成真实验证。

**回答结构**：问题 → 核心链路 → 实际验证对象 → 当前边界。

**证据**：`cli/index.ts`、`frameworks/ncom/framework.yaml`、`docs/v0.2.0-implementation-report.md`。

**继续追问**：为什么不用一个普通 README 加脚本？见第 3 题。

**不要这样答**：“这是一个能自动学习所有框架并自动修复代码的 Agent 平台。”

### 2. 为什么做这个项目？

**推荐回答**：小众框架常见问题是文档、源码、构建脚本和本地环境不一致。普通聊天式总结难以说明结论适用于哪个 commit、是否在实际环境运行过。我希望把框架事实绑定到 commit、配置、日志、Schema 和验证报告，减少把一次性试验写成普遍结论的风险。

**证据**：`AGENTS.md`、`docs/01-workflow-design.md`、NCom Run 006–010 报告。

### 3. 为什么是 CLI + 文件产物，而不是数据库和 Web 服务？

**推荐回答**：项目早期优先验证工作流本身。Markdown、YAML、JSON Schema 和 JSONL 容易审阅、版本控制和迁移，也适合保存本地运行证据。ADR-0001 的决策是先在真实任务中确认稳定重复操作，再开发最小 CLI；当前没有多用户、在线协作或查询性能需求，因此没有引入数据库和服务端复杂度。

**取舍**：优点是可审计、简单；缺点是大量产物后的索引、并发写入和访问控制尚未验证。

**证据**：`decisions/ADR-0001-workflow-first-cli-later.md`。

## 第二层：架构与工程实现

### 4. 核心调用链是什么？

**推荐回答**：CLI 入口解析命令。baseline 读取 `framework.yaml`，采集环境/Git，再用 spawn 顺序执行步骤和写独立日志；错误解析从日志生成 `errors.json`。Catalog 只扫描 tracked 文件，Symbol 层再分析已登记的 TS/TSX。Retrieval/Knowledge 基于 Snapshot 生成最小 Context。Task 创建后用 worktree、Policy、Plan 和 Acceptance 管理 Agent 修改，最后 inspect、verify、compare。Version 功能复用 Catalog/Symbol Diff 生成知识新鲜度影响。

**证据**：`cli/index.ts`、`cli/lib/*.ts`、[架构文档](02-系统架构与核心调用链.md)。

### 5. 为什么执行命令使用 spawn，而不是 exec 或 shell:true？

**推荐回答**：我需要保存实时 stdout/stderr、进程 PID、退出码和超时，并避免把路径和参数重新交给 shell 解析。`spawn(command, args, { shell:false })` 参数边界更清晰。Windows `.cmd` 不能直接执行时，项目只对 `.cmd/.bat` 显式适配 `cmd.exe /d /s /c`，并有中文和空格参数 fixture。

**证据**：`cli/lib/process.ts`、`test/framework-lab.test.ts`。

### 6. Schema 与 Validator 有什么区别？

**推荐回答**：Schema 用 Ajv 检查 JSON 的结构、必填字段和枚举，例如 run、task、acceptance。Validator 读取实际状态执行业务判断，例如 Policy 是否允许实际 Git diff、证据是否属于 Bundle、HTTP 是否达到预期、浏览器项是否仍需人工确认。Schema 正确不等于业务正确。

**证据**：`cli/lib/schema.ts`、`cli/lib/task.ts`、`schemas/acceptance.schema.json`。

## 第三层：真实故障与排查

### 7. 讲一个你实际排查过的构建故障

**推荐回答**：Run 009 在固定 NCom commit、Windows、Node 24.18 和 pnpm 10.26.1 下 build 失败。错误解析先区分了大量 ESLint 和 pnpm lifecycle 包装信息，首个 blocking 事件是 Sass `Can't find stylesheet to import`。我没有直接改原 worktree，而是创建独立候选 worktree，确认 `packages/all/build/shared.ts` 的 Sass additionalData 会注入包含 CJK 的绝对 `@use`。移除该冗余注入后，Run 010 的 build 通过，而允许失败的 lint 仍失败，最终状态正确为 partial。

**为什么可信**：同 commit、同环境、同 baseline steps，候选补丁只改一个 tracked 文件；Run 009/010 都保留。

**边界**：不证明所有 Windows 或所有 CJK 路径会失败，也不证明没有功能回归或上游已接受。

**证据**：`frameworks/ncom/reports/run-009-vs-run-010-cjk-sass-fix.md`。

### 8. 为什么 pnpm 的 ELIFECYCLE 不是根因？

**推荐回答**：ELIFECYCLE 是 pnpm 报告子命令失败的包装信息。项目日志解析器优先识别 ESLint、Sass、Vite、TypeScript、Node，再记录 pnpm lifecycle，避免包装错误覆盖具体错误。Run 009 的 blocking error 是 Sass import failure；Run 010 没有 Sass build failure，lifecycle 也不应被选成全局阻塞错误。

**证据**：`docs/v0.1.3-implementation-report.md`、`frameworks/ncom/runs/run-009/errors.json`。

### 9. HTTP 200 为什么不能表示浏览器功能通过？

**推荐回答**：HTTP 200 只说明指定资源可达。Run 007 中首页 HTML、Vite client 和部分静态资源是 200，但 HTML proxy 入口模块是 500，浏览器显示 Vite import-analysis overlay，页面未真正渲染。因此报告分别写 HTTP Smoke 和 Browser Behavior，浏览器项由人工 checklist 完成。

**证据**：`frameworks/ncom/reports/run-007-example-browser-smoke.md`。

## 第四层：Agent、Context 与 AI 追问

### 10. 项目里的 Agent 是怎么工作的？

**推荐回答**：项目不是自动启动 Agent，而是提供受控接口。Task 先绑定 commit、Context、允许路径、Acceptance 和验证步骤；外部 Agent 在 detached worktree 修改；Framework Lab 再独立 inspect Git diff、执行验证、比较 before/after，人工确认后才能关闭任务。

**证据**：`cli/lib/task.ts`、NCom task Handoff/verification report。

**不要这样答**：“系统会自动调用 Codex 把任务做完。”

### 11. 这算 RAG 吗？

**推荐回答**：不算。当前是确定性结构检索：基于 Catalog/Symbol、精确标识符、公开导出、关系深度、Scope 和证据完整度打分，读取有限行范围片段。没有 embedding、向量数据库、语义相似度或 LLM 检索调用。

**证据**：`docs/v0.1.7-implementation-report.md`、`cli/lib/retrieval.ts`。

### 12. 最小 Context 怎样避免幻觉或无关信息？

**推荐回答**：每个片段记录 source commit、文件 SHA256 与行号；只从 Catalog 登记文件读取；预算以完整候选/claim/snippet 为原子，不截断关键签名；Scope 不匹配的知识默认排除，并在 Manifest 写选择和排除理由。它降低无关上下文，不保证模型不会幻觉，因此仍需 Validator 和独立验证。

### 13. Context A/B 实验说明了什么？

**推荐回答**：它只说明在同一 NCom commit 的一次双会话探索中，有 Context 的 Agent 可以完成受限任务，且会话观察显示少做了部分核心源码与文档探索。两组都通过构建、开发服务和 HTTP；没有精确 usage、耗时、读取量，也没有完成真实浏览器点击，所以不能宣称固定 Token 节省或代码质量提升。

**证据**：`docs/v0.1.8-ncbutton-context-ab-experiment.md`。

## 第五层：质量与可靠性追问

### 14. 如何防止 Agent 改坏不该改的文件？

**推荐回答**：Change Policy 明确 allowed/denied path、最大 changed files/diff lines、lockfile/manifest 只读、untracked、binary 和冲突标记。inspect 不读取 Agent 自报，而是读取实际 Git 状态和 patch；违反规则可阻止后续验证或拒绝关闭。

### 15. 如何处理 verified 知识在新版本失效？

**推荐回答**：版本记录绑定 Catalog/Symbol Snapshot；Version Diff 复用已有差异；Evidence Impact 以精确 hash 判断 unchanged/relocated/changed/removed；再传播到 Claim 和 Knowledge Unit。verified Claim 即使源码未变，若运行证据属于旧 commit，仍需要目标版本重新验证，不能静默 carry-forward。

**证据**：`cli/lib/version.ts`、`docs/v0.2.2-implementation-report.md`。

## 压力追问

### 16. 代码是不是 Codex 写的？你到底会什么？

**推荐回答**：我把 AI 当作协作工具，但我能说明项目的真实边界、输入输出、测试和失败证据。例如我能解释为何 `spawn` 保持 shell:false、为何 CJK Sass 问题需要独立 worktree 对照、为何 HTTP 不能代替浏览器验证。无法独立解释的模块不会写进简历，并列入学习清单。

**不要这样答**：“都是 AI 写的，但应该没问题。”

### 17. 这是不是 Demo？

**推荐回答**：它目前是本地 CLI 原型，不是生产 SaaS；但不是只有页面的 Demo。NCom 有真实 commit、环境、Run 009/010 对照、任务 worktree、Policy、构建和 HTTP 证据。它仍缺第二框架、真实用户、部署与规模性能验证，我会明确说明。

### 18. 为什么不用现成 CI 或 Agent 框架？

**推荐回答**：CI 擅长固定仓库的持续检查，但这里需要学习陌生框架、保存 Evidence/Context/版本影响和受控外部 Agent 任务。Agent 框架能提供模型循环，但不能自动解决框架版本绑定、修改边界和独立验收。当前先实现最小可验证流程；未来如果重复需求被证明，再评估集成。
