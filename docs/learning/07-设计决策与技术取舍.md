# 设计决策与技术取舍

## 1. 先验证工作流，再开发最小 CLI

- **背景**：早期尚不清楚哪些框架操作会稳定重复。
- **候选**：直接做完整平台；先用文档和手工流程；先做最小 CLI。
- **选择**：先通过 Markdown/YAML/Schema 和 NCom 实验验证流程，再实现配置驱动 CLI。
- **优点**：减少过早抽象，CLI 的输入输出能基于真实证据设计。
- **缺点/风险**：早期人工操作多，Run 004–006 还出现了日志缺口。
- **后续**：只有第二框架也验证重复需求后，才考虑更通用适配层。
- **证据**：`decisions/ADR-0001-workflow-first-cli-later.md`。

## 2. 固定版本、环境和 dirty 状态

- **背景**：同一命令在不同 Node/pnpm/commit 或未提交改动下结果可能不同。
- **选择**：每个 Run 记录 OS、Node/npm/pnpm、Framework Lab commit、框架 commit、dirty 和 changed files；pnpm 使用仓库固定可执行路径。
- **优点**：避免“同一 commit”掩盖本地补丁；Run 009/010 可以形成受控对照。
- **缺点**：本地环境和原始日志可能不能全部公开。
- **不选择**：只在 README 写推荐版本，或使用 PATH 上任意 pnpm。

## 3. 文件产物 + JSON Schema，而非数据库

- **背景**：当前是单机、本地 CLI、单框架真实验证。
- **选择**：YAML 配置、JSON/JSONL 运行产物、Markdown 报告和 Ajv Schema。
- **优点**：Git 友好、可审阅、易于保留历史、无需服务部署。
- **缺点**：大规模查询、并发写入、访问控制和生命周期管理尚未解决。
- **不选择**：没有真实需求前引入 MySQL/Redis/消息队列。

## 4. 确定性结构检索，不交给 LLM 推断

- **背景**：框架源码变化快，模型摘要难以绑定版本和证据。
- **选择**：Catalog 只扫描 Git tracked 文件；Symbol 只分析 Catalog 登记 TS/TSX；检索按标识符、导出、关系、Scope 和诊断透明打分。
- **优点**：输出可复现，可引用 commit/hash/行号；不需要外部服务。
- **缺点**：不理解自然语言语义，不构建完整运行时调用图；中文任务依赖配置 alias。
- **不选择**：把 LLM 或模糊相似度当作事实迁移器。

## 5. 最小 Context 而不是整仓库投喂

- **背景**：整文件上下文噪声大、难核验、难控预算。
- **选择**：只输出入选 Candidate 的完整 claim/signature/有限代码片段，所有片段带 commit、hash、行号；预算不足时拒绝或裁剪候选，而不截断关键内容。
- **优点**：保留证据定位，减少无关材料。
- **风险**：缺少关键文件仍可能造成 Agent 决策不佳；字符数/4 不是实际 Token。
- **证据**：v0.1.7 Retrieval 实施报告、v0.2.1 Context 对照。

## 6. 受控 Agent 工作流，而非自主循环

- **背景**：陌生框架任务的主要风险是越界修改、无验证结论和不可观察行为。
- **选择**：Task + detached worktree + Handoff + Change Policy + Acceptance + Verification Plan + Compare + 人工 close。
- **优点**：Agent 可替换；修改和验证独立；手动项不被自动通过。
- **缺点**：需要人工启动 Agent 和确认浏览器，自动化程度较低。
- **不选择**：当前不实现自动 Agent 调用、自动接受、commit 或 push。

## 7. 分开 HTTP 与浏览器行为

- **背景**：服务可监听、首页 200、静态资源成功都不足以证明应用可交互。
- **选择**：HTTP 验证只记为 smoke；浏览器视觉、点击、Console/Network 保留 checklist 与 `manual_required`。
- **证据**：Run 007 首页/资源 200，但入口模块 500、浏览器 overlay；NCButton Task 18 自动项通过仍保持 `verification_partial`。
- **后续**：如引入浏览器自动化，须保留浏览器版本、可观察条件和人工补充边界。

## 8. 精确 Diff 与知识新鲜度传播

- **背景**：框架升级不应因同 package 有变化就重新学习全部知识。
- **选择**：Version 复用 Catalog/Symbol Diff；Evidence 只以精确 hash 判断 unchanged/relocated/changed/removed；结构变化不自动称 breaking change。
- **优点**：只为受影响 Topic 生成 Refresh Plan，保留历史发布知识。
- **风险**：精确 hash 不能理解语义等价；verified Claim 即使源码不变也可能需要目标 commit 重跑。
- **真实结果**：NCom `0eddf72 → a350b57` 有 85 文件、12 symbol、16 export 变化，但六个已发布单元未被人为标 stale，impact 为 0。

## 9. 不自动修复，使用最小对照实验

- **背景**：框架源码问题不能由工具擅自改写。
- **选择**：Run 009/010 在独立候选 worktree 只改 `shared.ts`，保留原 Run、原 worktree、日志和 lint 失败。
- **优点**：可以说明受控变量和实际构建结果。
- **边界**：补丁不等于上游接受，也不证明无回归。
