# 知识卡规范

## 定位

知识卡是绑定特定框架版本、带证据和验证记录的最小知识单元。它不是聊天摘要，也不是未经核实的 API 百科。

## 核心字段

字段以 [knowledge-card Schema](../schemas/knowledge-card.schema.json) 为准，包括身份、框架与 commit、状态、摘要、使用条件、规则、反模式、示例、证据、验证、可信度、时间和标签。

## 状态

- `draft`：候选知识，尚未完成验证。
- `verified`：证据与验证均满足当前规范，且绑定明确 commit。
- `conflicted`：可靠来源或实验结果存在未解决冲突。
- `deprecated`：知识不再适用，但为历史追踪而保留。
- `needs-review`：版本、来源或相关实现变化，需要重新验证。

## 生命周期

候选发现 → `draft` → 补充证据与实验 → `verified`。出现冲突转为 `conflicted`；框架升级、证据链接失效、验证环境显著变化或关联回归失败时转为 `needs-review`；被替代且确认不再适用时转为 `deprecated`。复核不得覆盖旧证据，应保留变更原因。

## 证据等级

从强到弱建议为：可定位源码与可复现实验、官方文档、官方示例、公开 issue/PR、其他公开材料。单一来源不自动等于事实；源码说明实现，实验说明特定环境行为，文档说明公开承诺，三者冲突时必须记录。

Schema 支持的证据类型为 `source`、`documentation`、`example`、`experiment`、`issue` 和 `pull-request`。

## 可信度

可信度表达当前证据对结论的支持程度，不替代状态或验证。建议使用 `low`、`medium`、`high`；只有明确 commit、可定位证据和成功复现齐备时才考虑 `high`。

## 版本绑定与验证

`framework_commit` 必须是实际观察的 commit；尚未锁定时只能创建 `draft`，且值为 `null`。验证记录包括方法、命令、环境、预期、实际结果和时间。无法执行的命令必须标记未运行。

## 反例与错误模式

记录不适用条件、常见误用、失败表现和反例。反例需要与正向结论采用相同证据标准，不能根据想象补全。

## 标记 needs-review 的条件

- 框架 commit 或依赖环境改变。
- 对应源码、文档或示例发生变化或不可访问。
- 受影响测试失败或出现新冲突证据。
- 卡片的验证时间超过项目约定周期。
- API、兼容性或行为边界无法在新版本复现。

## 禁止事项

- 将 AI 推断、搜索摘要或未执行示例直接标为 `verified`。
- 伪造 commit、命令、输出、日期或来源定位。
- 用“官方如此”代替具体链接和位置。
- 静默覆盖冲突、失败、反例或历史验证记录。
- 在未清除敏感信息时保存日志或截图。
